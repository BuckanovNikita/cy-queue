# cy-queue move, cancel, recover, archive, restore

Эти команды управляют уже поставленными в очередь [заданиями (job)](../../GLOSSARY.md#job): `move` меняет порядок ожидающих заданий, `cancel` отменяет задание, `recover` освобождает задание в состоянии [требуется восстановление (recovery required)](../../GLOSSARY.md#recovery-required), `archive` и `restore` скрывают завершённые задания из обычного `list` и возвращают их обратно.

## Примеры

```bash
cy-queue list --json                      # узнать текущую ревизию очереди (поле revision)
cy-queue move job-17 top --revision 42    # поставить job-17 первым среди ожидающих
cy-queue move job-17 after job-12 --revision 43   # поставить job-17 сразу после job-12 (ревизия после предыдущего move)
cy-queue cancel job-17                    # отменить задание
cy-queue recover job-17                   # восстановить задание в recovery_required
cy-queue archive job-15 job-16 job-17     # убрать завершённые задания в архив
cy-queue restore job-17                   # вернуть задание из архива
```

## Ссылки на задания и владелец

Каждая команда этой страницы принимает задание как `JOB`:

- [ссылка на задание (job reference)](../../GLOSSARY.md#job-reference) `job-<N>`, где `<N>` — номер, который `submit` и `list` печатают как `Job <N>`;
- полный ID задания из поля `id` вывода `--json`.

Другие формы (`17`, `Job 17`, `job-017`) не принимаются. Задание ищется только в [разделе хоста (host partition)](../../GLOSSARY.md#host-partition) текущего хоста, архивные задания тоже находятся. Если задания нет, команда печатает `Queue job reference is unknown in the local host partition; use job-N from list`. Сообщение не различает опечатку и задание другого хоста: ссылка неизвестна в разделе хоста текущего хоста.

[Владелец](../../GLOSSARY.md#owner) задания — пользователь Linux (UID), который его поставил в очередь. Кто что может:

| Команда | Кто может выполнить |
| --- | --- |
| `move` | любой пользователь хоста, для любого ожидающего задания, в том числе чужого |
| `cancel`, `archive`, `restore` | только владелец |
| `recover` | только владелец |

Для чужого задания `cancel`, `archive` и `restore` печатают `Only the effective job owner may change or execute this job`, `recover` печатает `Only the effective owner may recover this job`.

Все сообщения об ошибках печатаются в stderr с префиксом `cy-queue: `. Код завершения `1` означает отказ команды, код `2` — ошибку разбора аргументов (неизвестное направление, нет обязательного аргумента).

## move

Переносит ожидающее (`pending`) задание на другое место в очереди. Порядок очереди определяет, какое задание worker запустит раньше.

### Синтаксис и аргументы

```text
cy-queue move [-h] --revision REVISION [--json] JOB {up,down,top,bottom,before,after} [relative_job_id]
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `JOB` | обязателен | Задание, которое нужно перенести. |
| `direction` | обязателен | Направление: `up`, `down`, `top`, `bottom`, `before`, `after`. |
| `relative_job_id` | нет | Задание, относительно которого переносят. Обязателен для `before` и `after`. Для остальных направлений место не меняет, но если он указан, задание должно существовать, иначе команда отказывает с `Queue job reference is unknown in the local host partition; use job-N from list`. |
| `--revision` | обязателен | [Ревизия очереди (revision)](../../GLOSSARY.md#revision), которую вы видели в последний раз. |
| `--json` | выключен | Напечатать очередь после переноса в JSON. |

Направления:

| Направление | Что делает |
| --- | --- |
| `up` | на одно место выше среди ожидающих заданий |
| `down` | на одно место ниже среди ожидающих заданий |
| `top` | первым среди ожидающих заданий |
| `bottom` | последним среди ожидающих заданий |
| `before` | сразу перед `relative_job_id` |
| `after` | сразу после `relative_job_id` |

### Как это работает

1. Команда читает раздел текущего хоста и сравнивает `--revision` с текущей ревизией. Ревизию печатает первая строка `list` (`revision N`) и поле `revision` в `list --json`. Ревизия растёт при любом изменении очереди: новое задание, перенос, отмена, смена состояния, причины ожидания или прогресса любого задания, архив. Пока worker запускает задания или задание сообщает прогресс, ревизия меняется и без ваших действий. Если очередь изменилась с момента, когда вы взяли номер, команда ничего не меняет и печатает `Stale queue revision; refresh before reordering`. Снова выполните `list`, возьмите новую ревизию и повторите `move`.
2. Команда находит `JOB` и, если он указан, `relative_job_id`.
3. Переносить можно только задание в состоянии `pending`. Для любого другого состояния команда печатает `Only pending jobs can be reordered`.
4. Позиции считаются только среди ожидающих заданий. `relative_job_id` тоже должен быть другим ожидающим заданием. Без него, с тем же заданием или с заданием не в `pending` команда печатает `Relative ordering requires another existing job`.
5. Если задание уже стоит на нужном месте (`up` или `top` для первого, `down` или `bottom` для последнего), команда ничего не записывает и ревизия не меняется.
6. Иначе команда записывает перенос, и ревизия увеличивается на 1.

### Результат

Команда печатает очередь так же, как `list` без флагов: первую строку с ревизией и строки заданий без архивных, с причинами ожидания и выделенными GPU, вычисленными так же, как в `list` (формат строки описан в [list](list.md)). С `--json` печатается тот же объект, что у `list --json` ([JSON](../formats/json.md)). Если текущие значения прочитать не удалось, перенос всё равно записан: команда печатает записанные значения и предупреждение на stderr (см. [JSON](../formats/json.md)).

```text
my-queue | gpu-host | revision 43 | archived 0 | warnings 0
1	Job 17 · my-run	uid=1000	pending	request=1	allocation=-	Owner worker unavailable
2	Job 12 · my-run	uid=1000	pending	request=1	allocation=-	Owner worker unavailable
```

#### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | задание перенесено или уже было на месте |
| `1` | отказ: устаревшая ревизия, задание не найдено, не `pending`, нет относительного задания |
| `2` | ошибка аргументов, например нет `--revision` |

### Частые ошибки

| Сообщение | Причина и что делать |
| --- | --- |
| `Stale queue revision; refresh before reordering` | Очередь изменилась после того, как вы взяли ревизию. Выполните `cy-queue list` и повторите с новой ревизией. |
| `Only pending jobs can be reordered` | Задание уже запущено, завершено или отменено. |
| `Relative ordering requires another existing job` | Для `before` и `after` не указано другое ожидающее задание. |
| `cy-queue move: error: the following arguments are required: --revision` | Добавьте `--revision`. |

## cancel

Отменяет ваше задание.

### Синтаксис и аргументы

```text
cy-queue cancel [-h] [--json] JOB
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `JOB` | обязателен | Задание, которое нужно отменить. |
| `--json` | выключен | Напечатать [запись задания (job record)](../../GLOSSARY.md#job-record) в JSON. |

### Как это работает

1. Команда находит задание и проверяет, что вы его владелец.
2. Задание в `pending` сразу становится `cancelled`, worker его уже не запустит.
3. Задание в `starting` или `running` становится `cancelling`. Команда записывает запрос на остановку и не ждёт её. Задание сохраняет [выделенные GPU (allocation)](../../GLOSSARY.md#allocation), пока процессы не завершатся, после чего его состояние становится `cancelled`.
4. Для задания в `recovery_required` команда записывает запрос на отмену, но состояние не меняет. Чтобы освободить такое задание, выполните `recover`.
5. Задание в `completed`, `failed` или `cancelled` не меняется, повторная отмена не считается ошибкой.

### Результат

Команда печатает строку `Job <N> · <имя>: <состояние>` с состоянием после команды:

```text
Job 17 · my-run: cancelled
```

Если задание осталось в `recovery_required`, команда печатает ту же строку, а в stderr добавляет подсказку:

```text
Job 17 · my-run: recovery_required
cy-queue: job-17 stays recovery_required; run cy-queue recover job-17 to stop what is left of it
```

С `--json` печатается запись задания ([JSON](../formats/json.md)), подсказки нет. Дальше следите за заданием через `cy-queue list`.

#### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | запрос принят (в том числе для уже завершённого задания) |
| `1` | задание не найдено или чужое |
| `2` | ошибка аргументов |

### Частые ошибки

| Сообщение | Причина и что делать |
| --- | --- |
| `Only the effective job owner may change or execute this job` | Задание поставил другой пользователь. Отменить его может только владелец. |
| `Queue job reference is unknown in the local host partition; use job-N from list` | Ссылка неизвестна в разделе текущего хоста: опечатка или задание другого хоста. Возьмите `job-<N>` из `cy-queue list`. |

## recover

Освобождает задание, которое осталось в состоянии `recovery_required`: очередь потеряла связь с процессами задания (например, умер его [guardian (процесс-надзиратель задания)](../../GLOSSARY.md#guardian)), и они могут продолжать занимать GPU уже без [резерва (reservation)](../../GLOSSARY.md#reservation).

### Синтаксис и аргументы

```text
cy-queue recover [-h] [--json] JOB
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `JOB` | обязателен | Задание в состоянии `recovery_required`. |
| `--json` | выключен | Напечатать запись задания в JSON. |

### Как это работает

1. Команда находит задание и проверяет, что вы его владелец.
2. Состояние должно быть `recovery_required`, иначе команда отказывает.
3. Команда проверяет guardian задания. Если он ещё жив в текущей загрузке хоста, команда отказывает.
4. Команда на время восстановления сама занимает GPU задания. Если их резерв всё ещё держит работающий процесс, команда отказывает.
5. Команда записывает отмену, останавливает оставшиеся процессы задания, проверяет, что их не осталось, и освобождает GPU.
6. Задание становится `cancelled` с ошибкой `Owner recovered abandoned execution after verified descendant cleanup`.

### Результат

```text
Job 17 · my-run: cancelled
```

С `--json` печатается запись задания ([JSON](../formats/json.md)).

#### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | задание восстановлено и отменено |
| `1` | отказ (см. ниже) |
| `2` | ошибка аргументов |

### Частые ошибки

| Сообщение | Причина и что делать |
| --- | --- |
| `Only jobs requiring recovery can be recovered` | Задание не в `recovery_required`. Для обычной отмены выполните `cancel`. |
| `Only the effective owner may recover this job` | Задание поставил другой пользователь. |
| `Guardian is still alive; cancel it before attempting recovery` | Guardian задания ещё работает. Выполните `cancel` и дождитесь, пока он завершится. |
| `GPU guardian still owns its locks; recovery refused` | Резерв GPU задания всё ещё у работающего процесса. Повторите позже. |
| `Cannot verify model process cleanup: /proc access denied for PIDs [...]; GPU lease remains owned` | Команда не смогла прочитать в `/proc` перечисленные процессы вашего пользователя, поэтому не может подтвердить, что процессов задания не осталось. Так бывает, когда `cy-queue` запущен в контейнере или пространстве имён, откуда другие ваши процессы не читаются. Задание остаётся в `recovery_required`. Выполните `recover` из обычного сеанса на хосте. |
| `Queue job reference is unknown in the local host partition; use job-N from list` | Ссылка неизвестна в разделе текущего хоста: опечатка или задание другого хоста. Возьмите `job-<N>` из `cy-queue list`. |

## archive

Помечает ваши завершённые задания как [архивные](../../GLOSSARY.md#archive), чтобы они не мешали в обычном `list`.

### Синтаксис и аргументы

```text
cy-queue archive [-h] [--json] JOB [JOB ...]
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `JOB` | обязателен, один или несколько | Задания, которые нужно убрать в архив. Повтор одного задания учитывается один раз. |
| `--json` | выключен | Напечатать очередь после команды в JSON. |

### Как это работает

1. Команда находит все задания из списка, включая уже архивные.
2. Она проверяет всё сразу: каждое задание должно быть вашим и в одном из состояний `completed`, `failed`, `cancelled`. Если хоть одно не подходит, команда ничего не меняет.
3. Для каждого задания команда записывает отметку архива. Уже архивное задание пропускается без ошибки.
4. Архив меняет только видимость: задание, его записи и логи остаются, ничего не удаляется. Ревизия очереди растёт, если хотя бы одно задание получило отметку.

### Результат

Команда печатает `Archived <число> job(s)`, где число — количество разных заданий в команде, включая уже архивные, затем очередь в виде `list` без архивных заданий. Счётчик `archived` в первой строке показывает число архивных заданий. Перед записью команда читает очередь так же, как `list`. Если это чтение не удалось, команда ничего не меняет и печатает ошибку `cy-queue: ...`, код `1`. Если причины ожидания и GPU не удалось прочитать уже после записи отметки, отметка остаётся: команда печатает записанные значения и предупреждение на stderr, как `move`.

```text
Archived 1 job(s)
my-queue | gpu-host | revision 44 | archived 1 | warnings 0
```

Архивные задания показывает `cy-queue list --archived`, все вместе — `cy-queue list --all`; в обоих видах у архивного задания после состояния стоит `(archived)`, например `cancelled (archived)` (см. [list](list.md)). С `--json` строка `Archived ...` не печатается, печатается только очередь ([JSON](../formats/json.md)).

#### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | задания в архиве |
| `1` | задание не найдено, чужое или не завершено |
| `2` | не указан ни один `JOB` |

### Частые ошибки

| Сообщение | Причина и что делать |
| --- | --- |
| `Only completed, failed or cancelled jobs can be archived` | Одно из заданий ещё не завершено. Уберите его из списка или дождитесь завершения. |
| `Only the effective job owner may change or execute this job` | Одно из заданий чужое. |

## restore

Возвращает ваши задания из архива в обычный `list`.

### Синтаксис и аргументы

```text
cy-queue restore [-h] [--json] JOB [JOB ...]
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `JOB` | обязателен, один или несколько | Задания, которые нужно вернуть из архива. |
| `--json` | выключен | Напечатать очередь после команды в JSON. |

### Как это работает

1. Команда находит задания и проверяет, что все они ваши.
2. Для каждого архивного задания она снимает отметку архива. Задание без отметки пропускается без ошибки.

### Результат

Команда печатает `Restored <число> job(s)`, где число — количество разных заданий в команде, включая те, что не были в архиве, затем очередь в виде `list`, уже с возвращёнными заданиями. С `--json` печатается только очередь. Как и `archive`, команда ничего не меняет, если очередь не удалось прочитать до записи. Если значения не удалось прочитать уже после записи, изменение остаётся, печатаются записанные значения и предупреждение.

#### Коды завершения

| Код | Значение |
| --- | --- |
| `0` | задания возвращены |
| `1` | задание не найдено или чужое |
| `2` | не указан ни один `JOB` |

### Частые ошибки

| Сообщение | Причина и что делать |
| --- | --- |
| `Only the effective job owner may change or execute this job` | Одно из заданий чужое. Команда ничего не возвращает из архива. |
| `Queue job reference is unknown in the local host partition; use job-N from list` | Ссылка неизвестна в разделе текущего хоста. Возьмите `job-<N>` из `cy-queue list --archived`. |
