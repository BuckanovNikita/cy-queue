# cy-queue list и cy-queue tui

`cy-queue list` печатает [очередь](../../GLOSSARY.md#queue) (queue) этого хоста: задания (job) в порядке очереди, их состояние, GPU и причину ожидания. `cy-queue tui` показывает то же в интерактивном интерфейсе терминала, обновляет его сам и позволяет переставлять, отменять и архивировать задания.

## Примеры

```bash
cy-queue list
```

Показывает задания хоста без архивных.

```bash
cy-queue list --all --json
```

Печатает все задания, включая архивные, одной JSON-записью.

```bash
cy-queue tui
```

Открывает интерактивный [вид очереди (queue view)](../../GLOSSARY.md#queue-view).

## Состояния заданий

| Состояние | Значение | Что делать |
| --- | --- | --- |
| `pending` | Задание ждёт в очереди своего worker и свободных GPU на весь запрос; причина в конце строки. | Ничего, если причина ожидаемая. Если `Owner worker unavailable`, запустите [`cy-queue worker`](worker.md). Порядок можно изменить через [`move`](jobs.md), отменить через [`cancel`](jobs.md). |
| `starting` | Worker занял GPU и запускает процесс задания. | Ждать. Отменить можно через `cancel`. |
| `running` | Процесс задания работает на выделенных GPU. | Следить через `list`, `tui` и журнал задания ([Состояние на диске](../state.md#что-задание-оставляет-в-рабочем-каталоге)). Остановить можно через `cancel`. |
| `cancelling` | После `cancel` задание останавливается и держит GPU, пока его процессы не завершатся. | Ждать перехода в `cancelled`. |
| `completed` | Процесс задания завершился с кодом `0`. | Смотреть результат в ClearML и журнале. Можно [`archive`](jobs.md). |
| `failed` | Процесс задания завершился с ненулевым кодом или его не удалось довести до конца; причина в поле `error` (`--json`) и в журнале задания. | Прочитать журнал задания, исправить причину, поставить задание в очередь заново. Можно `archive`. |
| `cancelled` | Задание отменено до запуска, остановлено через `cancel` или очищено через `recover`. | Можно `archive`. |
| `recovery_required` | [Требуется восстановление](../../GLOSSARY.md#recovery-required) (recovery required): очередь не знает, остались ли процессы задания. Резерв GPU держит guardian задания: если guardian пропал, GPU в `gpu list` уже без задания, хотя оставшиеся процессы могут его занимать. | Владелец выполняет [`recover`](jobs.md). Почему задание попало в это состояние, описано в [worker](worker.md#когда-задание-требует-восстановления). |

`completed`, `failed` и `cancelled` — конечные состояния; только такие задания можно архивировать.

## cy-queue list

### Синтаксис и аргументы

```text
cy-queue [--root ROOT] list [-h] [--host HOST] [--json] [--archived | --all]
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `--archived` | | Показывает только архивные задания. |
| `--all` | | Показывает и архивные, и неархивные задания. С `--archived` не сочетается. |
| `--host HOST` | локальный хост | Читает [раздел хоста](../../GLOSSARY.md#host-partition) (host partition) с ID `HOST` (поле `host_id` в `--json`). |
| `--json` | | Печатает одну JSON-запись вместо текста. |
| `-h`, `--help` | | Печатает справку и завершает работу. |

Без `--archived` и `--all` показываются все задания, кроме архивных. Архивным считается только задание в конечном состоянии с отметкой [архива](../../GLOSSARY.md#archive).

### Как это работает

1. Для локального хоста команда сначала читает файлы статуса ваших заданий в [рабочем каталоге (project)](../../GLOSSARY.md#project) и публикует их прогресс и ссылку на задачу ClearML.
2. Читает раздел хоста в каталоге очереди.
3. Для каждого задания `pending` заново вычисляет причину ожидания по живым worker, их GPU, резервам и удержаниям. Для заданий `starting`, `running`, `cancelling` и `recovery_required` берёт GPU из резервов в каталоге координации.
4. Отбирает задания по виду (`--archived`, `--all`) и печатает их.

С `--host`, указывающим другой хост, шаги 1 и 3 пропускаются: команда только читает записанное на том хосте, ничего не меняет, а причины ожидания и `allocation=` показывает такими, какими их последний раз записали там.

### Результат

Первая строка — заголовок:

```text
my-queue | gpu-host | revision 4 | archived 1 | warnings 0
```

| Часть | Значение |
| --- | --- |
| `my-queue` | Ключ `name` из [конфигурации](../configuration.md#раздел-queue). |
| `gpu-host` | Имя локального хоста. Для любого другого значения `--host` печатается `Remote host`; сам ID есть в поле `host_id` вывода `--json`. |
| `revision N` | Текущая [ревизия очереди](../../GLOSSARY.md#revision) (revision); её требует `move --revision`. |
| `archived N` | Сколько заданий в разделе хоста помечены архивными, независимо от вида. |
| `warnings N` | Сколько показанных заданий имеют [предупреждение обновления (refresh warning)](../../GLOSSARY.md#refresh-warning). |

Затем по строке на задание, поля разделены табуляцией:

```text
1	Job 2 · my-run	uid=1000	pending	request=3	allocation=-	Owner worker unavailable
```

| Поле | Значение |
| --- | --- |
| `1` | Позиция в показанном списке, сверху вниз в порядке очереди. |
| `Job 2 · my-run` | Номер задания и [имя задания](../../GLOSSARY.md#label) (label), а без имени — команда задания. На задание ссылаются как `job-2`. |
| `uid=1000` | UID [владельца](../../GLOSSARY.md#owner). |
| `pending` | Состояние; у архивного задания добавлено ` (archived)`, например `cancelled (archived)`. |
| `request=` | [Запрос GPU](../../GLOSSARY.md#gpu-request): число GPU для `--gpus` или GPU через запятую для `--devices`. |
| `allocation=` | [Выделенные GPU](../../GLOSSARY.md#allocation) (allocation) через запятую, `-`, если их нет. |
| причина | [Причина ожидания](../../GLOSSARY.md#waiting-reason) (waiting reason) задания `pending`. У задания в другом состоянии поле пустое. |
| предупреждение | Только при сбое обновления: ещё одно поле после табуляции. |

GPU локального хоста печатаются физическими номерами, как в `gpu list`. GPU, которую номером показать нельзя (например, на другом хосте), печатается [коротким именем](../../GLOSSARY.md#gpu-label) `gpu-<word>-<word>-<word>-<word>`.

Формат `--json` описан в [Формате вывода `--json`](../formats/json.md#вид-очереди).

#### Причины ожидания

| Причина | Значение |
| --- | --- |
| `Owner worker unavailable` | У владельца задания нет живого worker на этом хосте. |
| `Owner GPU telemetry unavailable` | Worker владельца жив, но не сообщил ни об одной GPU: он ещё не выполнил первый опрос, не смог прочитать их память или ему не видна ни одна GPU (например, worker запущен с пустым `CUDA_VISIBLE_DEVICES`). |
| `Requested GPUs are outside the owner worker CUDA visibility` | Задание с `--devices` просит GPU, которых не видит worker владельца. |
| `Requested GPU allocation is disabled by an operator hold` | На одной из GPU задания с `--devices` стоит [удержание](../../GLOSSARY.md#hold) (hold). |
| `Waiting for the complete exact GPU allocation` | Не все GPU задания с `--devices` свободны: они заняты, в резерве или их память не ниже порога. |
| `Waiting for GPU capacity: operator holds disable visible devices` | Свободных GPU меньше, чем просит `--gpus`, и на части видимых GPU стоит удержание. |
| `Waiting for GPU capacity: N requested, M available` | Свободных GPU меньше, чем просит `--gpus`: запрошено `N`, свободно `M`. |
| `Waiting for an earlier runnable job` | Задание поместилось бы, но первым запустится более раннее задание (возможно, другого пользователя). |
| `Ready for owner worker admission` | Задание первое, которое может запуститься; worker владельца запустит его на ближайшем опросе. |

Эти причины записывает worker, и они видны с `--host` и у заданий с предупреждением обновления:

| Причина | Значение |
| --- | --- |
| `GPU memory telemetry unavailable` | Worker владельца не смог прочитать память своих GPU. |
| `GPU memory is unavailable or at least <порог> GiB at startup` | При последней проверке перед стартом память выделенной GPU была недоступна или не ниже порога, и задание вернулось в очередь. |
| `GPU allocation was freed before startup` | Резерв GPU сняли (`gpu free`) перед стартом, и задание вернулось в очередь. |

#### Предупреждения обновления

Если команда не может прочитать снимок или файл статуса вашего задания (файл недоступен, вне рабочего каталога, больше допустимого размера или повреждён), она не падает. Строка задания получает поле `Status unavailable; showing last recorded state`, а заголовок считает его в `warnings`. Состояние задания при этом показано последнее записанное.

#### Коды завершения

| Код | Когда |
| --- | --- |
| `0` | Очередь напечатана. |
| `1` | Ошибка конфигурации или доступа к очереди; сообщение `cy-queue: <ошибка>` в stderr. |
| `2` | Неверный аргумент, например `--archived` вместе с `--all`. |

### Частые ошибки

| Сообщение | Причина и решение |
| --- | --- |
| `cy-queue list: error: argument --all: not allowed with argument --archived` | Указаны оба вида. Выберите один. |
| Пустой список с `--host`, в заголовке `Remote host` | Возможно, ID введён с ошибкой: в каталоге очереди нет раздела с таким ID; команда не сообщает об ошибке и завершается с кодом `0`. Возьмите `host_id` из `cy-queue list --json` на нужном хосте. |
| Все задания `pending` с `Owner worker unavailable` | Не запущен worker. Запустите [`cy-queue worker`](worker.md). |

## cy-queue tui

### Синтаксис и аргументы

```text
cy-queue [--root ROOT] tui [-h]
```

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `-h`, `--help` | | Печатает справку и завершает работу. |

### Как это работает

1. Интерфейс показывает таблицу заданий с колонками `Position`, `Job`, `Owner`, `State`, `Request`, `Allocation`, `Waiting reason`, `Progress`, `ClearML`, `Status diagnostic`. Они соответствуют полям строки [`list`](#результат); `Progress` показывает дробный прогресс в процентах, `ClearML` — `Open task (o)`, если у задания есть ссылка на задачу ClearML, `Status diagnostic` — предупреждение обновления. Показывается только локальный хост: флага `--host` у `tui` нет.
2. Над таблицей строка состояния: имя очереди, хост, вид (`Main`, `Archived`, `All`), число архивных заданий, предупреждений, ревизия и напоминание `Closing this view leaves workers running`.
3. Каждые 2 секунды интерфейс перечитывает очередь, как `list`, и сохраняет выбранную строку. Если очередь прочитать не удалось, строка состояния показывает `Queue unavailable: <ошибка>`, а таблица остаётся прежней.
4. Действия выполняются над выбранной строкой. Ошибка действия появляется во всплывающем уведомлении, после чего таблица обновляется.

Клавиши:

| Клавиша | Действие |
| --- | --- |
| `u` | Поднять задание на одну позицию среди заданий `pending` (`move up`). |
| `d` | Опустить задание на одну позицию среди заданий `pending` (`move down`). |
| `t` | Поставить задание перед всеми заданиями `pending` (`move top`). |
| `g` | Поставить задание после всех заданий `pending` (`move bottom`). |
| `b` | Поставить задание перед другим: открывается список других заданий `pending` для выбора цели (`move before`). |
| `a` | Поставить задание после другого (`move after`), так же с выбором цели. |
| `Escape` | Закрыть список выбора цели. |
| `c` | Отменить задание (`cancel`). |
| `r` | Восстановить задание (`recover`). |
| `x` | Архивировать задание (`archive`). |
| `s` | Вернуть задание из архива (`restore`). |
| `v` | Сменить вид по кругу: обычный, архивные, все; заодно закрывает список выбора цели. |
| `o` | Открыть задачу ClearML задания в браузере. |
| `q` | Закрыть интерфейс. |

Ограничения действий те же, что у команд на странице [jobs](jobs.md): переставлять можно только задания `pending` (любого владельца); отменять, восстанавливать, архивировать и возвращать из архива может только владелец. Перестановка использует ревизию, показанную на экране; если очередь успела измениться, придёт ошибка о старой ревизии, и после обновления можно повторить.

### Результат

Интерфейс ничего не печатает. Закрытие (`q`) не останавливает ни worker, ни задания.

#### Коды завершения

| Код | Когда |
| --- | --- |
| `0` | Интерфейс закрыт. |
| `1` | Ошибка конфигурации, доступа к очереди при запуске или не установлен Textual; сообщение `cy-queue: <ошибка>` в stderr. |
| `2` | Неверный аргумент. |

### Частые ошибки

| Сообщение | Причина и решение |
| --- | --- |
| `cy-queue: The cy-queue installation is missing textual; reinstall its default dependencies` | В окружении нет пакета Textual. Переустановите cy-queue с зависимостями по умолчанию ([Установка](../setup.md)). |
| `Choose a pending job with another pending target` | `b` или `a` нажаты на задании не в `pending` или других заданий `pending` нет. |
| `Task link is unavailable` | Ссылка на задачу ClearML не `http` или `https`. |
| `No browser is available to open the task` | На машине не найден браузер. Откройте ссылку `clearml_url` из `cy-queue list --json` вручную. |
| `Stale queue revision; refresh before reordering` | Очередь изменилась между обновлением экрана и перестановкой. Повторите после обновления. |
